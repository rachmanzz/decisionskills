## Separate evidence discovery from reference persistence

- ID: `DEC-20261028-200624`
- Decided at: `2026-10-28T20:06:24+07:00`
- Scope: `decision-history`
- Tags: `workflow`, `evidence`, `github`, `references`, `read-only`
- Supersedes: none
- Related: `DEC-20261028-200242`
- References: none
- Source: `user-request`
- Integrity SHA256: `c1e3c22e6dad9bd9e907fbafa44e7a77408679928f69c309c5a7302297160991`

### Decision

Evidence discovery is read-only by default. The agent must first inspect the source and add argumentation that distinguishes facts, interpretation, relevance, limitations, and conflicts. This workflow applies with a GitHub repository or without one. The agent may create a ref only after an explicit persistence request or when durable evidence is required, and may record a decision without a ref when the evidence is temporary or a simple source link is sufficient.

### Rationale

The GitHub helper and manual reference workflow needed explicit steps for discovery versus persistence and for cases with or without a repository.

### Consequences

- Searching or analyzing evidence does not unexpectedly append files or decisions.
- Durable references are created deliberately and linked only after their context and argumentation are clear.

### Agent action

Use read-only discovery first, then present argumentation, then choose with-ref or without-ref before recording and validating a decision.

## Align GitHub snapshots with the reference file schema

- ID: `DEC-20261028-200242`
- Decided at: `2026-10-28T20:02:42+07:00`
- Scope: `decision-history`
- Tags: `github`, `references`, `schema`, `consistency`
- Supersedes: none
- Related: `DEC-20261028-200040`
- References: none
- Source: `user-request`
- Integrity SHA256: `e1900e21ec761a1e5b1b6da64ed90a45982da5159016cb9a603a9ea480b163d1`

### Decision

GitHub reference snapshots must use the standard Markdown reference structure: Type, Decision, source metadata, Retrieved at, URL, Content SHA256, a Context section, and an Evidence section containing the extracted Markdown. The snapshot is a ref file, not a decision block, and must remain append-only.

### Rationale

The first helper output was valid Markdown but used a custom Extracted content section and omitted the standard Type and Context/Evidence structure.

### Consequences

- Generated GitHub refs are consistent with manually written refs and easier for agents and humans to read.

### Agent action

Use the standardized snapshot output when saving GitHub context as ref evidence.

## Provide a read-only GitHub Markdown reference helper

- ID: `DEC-20261028-200040`
- Decided at: `2026-10-28T20:00:40+07:00`
- Scope: `decision-history`
- Tags: `github`, `references`, `read-only`, `raw-content`
- Supersedes: none
- Related: none
- References: none
- Source: `user-request`
- Integrity SHA256: `13e128d03c1fabde8e3687517cd1edc8617655a3a825d838cbbc0f55954620fd`

### Decision

Provide a Python helper that accepts a GitHub repository, Markdown path, and section IDs, fetches the file through raw.githubusercontent.com, extracts the requested sections, and optionally writes a new local ref snapshot. The helper must be read-only by default, must not use a browser, must not overwrite an existing snapshot, and must preserve source URL, revision, retrieval timestamp, and extracted-content SHA256.

### Rationale

Agents need a deterministic way to find GitHub Markdown context from repo, path, and IDs without manually opening a browser.

### Consequences

- Temporary context can be printed without changing project files.
- Durable evidence can be saved as an append-only local ref and linked with record_decision.py --ref.

### Agent action

Run find_github_reference.py when a user provides a GitHub repo, Markdown path, and section ID; validate the decision history after recording a ref.

## Handle validation failures without mutating decision history

- ID: `DEC-20261028-193804`
- Decided at: `2026-10-28T19:38:04+07:00`
- Scope: `decision-history-safety`
- Tags: `validation`, `references`, `append-only`, `agy`
- Supersedes: none
- Related: `DEC-20261028-193217`
- References: none
- Source: `user-report`
- Integrity SHA256: `0d6297903ad8bfdf984d03eeb3972bfc7aa07397e0d98142e0254c952195c87a`

### Decision

Treat validation failures as reportable diagnostics: preserve the failed decision block, keep the exact validator output, and correct forward with a new decision using supersedes when needed. Use --ref only for existing local files relative to .knowledges/decisions/; record external URLs with --source or in a local ref document.

### Rationale

AGY passed an external GoSuite URL through --ref and also produced a literal backslash-n sequence. The validator correctly rejected the missing local reference, but the failure was wrongly treated as a reason to delete and recreate the decision.

### Consequences

- Agents can distinguish a malformed record from an invalid history and must report the validator result honestly.
- External web sources remain traceable without being mistaken for local reference files.

### Agent action

Never delete or edit a failed decision block; inspect the error and append a correction linked with supersedes when required.


### Decision

Store multiple decisions in a month-level or date-level Markdown history file. Add every new decision block at the top of the selected file. Keep detailed references in the separate ref directory.

### Rationale

A period file keeps related history together while preserving the append-only order of decisions.

### Consequences

- The skill and its recorder must prepend new blocks without editing, reordering, or deleting older blocks.

### Agent action

Read the period files before consequential work and use the newest applicable decision block.
