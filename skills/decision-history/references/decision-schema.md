# Decision schema

Each period file is a Markdown file containing multiple decision blocks. New blocks use Markdown-only metadata followed by human-readable sections so people and agents can search them cheaply.

## File location

Store the period file at:

```text
.knowledges/decisions/YYYY-MM.md
# or .knowledges/decisions/YYYY-MM-DD.md
```

Use a numeric suffix with at least two digits in the decision ID when more than one decision is created in the same second (`-02` through `-99`, then `-100` and onward). Reference documents belong in:

```text
.knowledges/decisions/ref/
```

Paths in `refs` are relative to `.knowledges/decisions/` and must point to existing Markdown files under `ref/`. New decisions must be inserted before the previous first decision block. Existing blocks must remain byte-for-byte unchanged.

For new Markdown blocks, the ID's `YYYYMMDD-HHMMSS` portion and the month/date period filename must match `decided_at` in its stated timezone. Older YAML records remain historical and are not rewritten to meet this newer consistency rule.

## Decision block

````markdown
<!-- decision:start -->
## Use PostgreSQL as the primary database

- ID: `DEC-20261028-153000`
- Decided at: `2026-10-28T15:30:00+07:00`
- Scope: `database`
- Tags: `architecture`, `data`
- Supersedes: none
- Related: none
- References: none
- Reference SHA256: none
- Source: `conversation`
- Integrity SHA256: `...`

### Decision

Use PostgreSQL as the primary database for this project.

### Rationale

PostgreSQL provides the required relational features and transaction guarantees.

### Consequences

- Database migrations must support PostgreSQL.
- Local development should use PostgreSQL-compatible tooling.

<!-- decision:end -->
````

Required fields:

- `id`: unique, stable identifier beginning with `DEC-`.
- `title`: concise human-readable title.
- `decided_at`: ISO 8601 timestamp including timezone.
- `scope`: project, subsystem, or another clear boundary.

Recommended fields:

- `tags`: searchable terms.
- `supersedes`: IDs of decisions replaced by this one.
- `related`: IDs that provide context without being replaced.
- `refs`: optional paths to existing detailed supporting Markdown records under `.knowledges/decisions/ref/`. They must resolve inside `ref/`, including through symlink checks. They are local files, not web URLs.
- `reference_hashes` (`Reference SHA256`): generated `path=hash` entries for referenced files. The validator uses these to detect edits to referenced historical evidence.
- `source`: conversation, issue, pull request, document, external URL, or other origin. Put web URLs here, or cite them inside a local `ref/` document.
- `integrity_sha256`: generated by the recording helper to detect later edits.

Do not add a mutable `status` field. A decision is considered superseded when a newer decision lists its ID in `supersedes`; the old file remains unchanged.
The superseding decision's timestamp must be equal to or later than the decision it replaces, even when they are stored in different period files.

The `### Decision` section is required. It must contain a direct statement of what was decided and must be understandable without reading a reference file. `Rationale`, `Consequences`, and `Agent action` are optional body sections; `References` is optional metadata.

## Body sections

Use these sections inside each decision block when applicable:

```markdown
### Decision

Use PostgreSQL as the primary database for this project.

### Rationale

PostgreSQL provides the required relational features and transaction guarantees.

### Consequences

- Decisions can be searched with normal text search.
- Decisions are tracked by version control.
- Decisions do not depend on an external database.

### Agent action

Before making architectural or workflow changes, the AI must check relevant decisions.
```

Keep each decision block concise. Put long evidence, transcripts, diagrams, or research notes in a separate reference file named after the decision ID. A correction or new interpretation must be represented by a new record rather than silently changing an old reference.

If validation fails because a reference is missing, points to an external URL, or contains malformed escaping, preserve the failed record and report the exact error. Record corrected intent in a new decision using `supersedes` when the old ID is parseable; otherwise cite the failing file and block. The old error remains a strict-validation failure even after a correction. Never rewrite or delete the failed record or present the whole history as valid when it is not.

## Reference file format

Reference files are optional Markdown files stored under `.knowledges/decisions/ref/`. Create them before recording a decision so the path can be validated. The `refs` field stores a path relative to `.knowledges/decisions/`, for example `ref/DEC-20261028-193804.md`.

A reference file should be self-describing and normally include:

```markdown
# Reference for DEC-20261028-193804

- Decision: `DEC-20261028-193804`
- Type: External project context
- Retrieved at: `2026-10-28T19:30:00+07:00`
- URL: https://example.com/project

## Context

Why this source is relevant to the decision.

## Evidence

Relevant facts, observations, or concise excerpts.

## Interpretation

Why the evidence is relevant to the decision. Clearly distinguish interpretation from facts copied or summarized from the source.

## Limitations

Known gaps, assumptions, freshness concerns, or conflicts with other evidence.
```

Use `--source` for a simple external URL. Do not put the URL itself in `--ref`, and do not create an empty reference file. Existing reference files are immutable historical records; create a new file and link it from a new decision when the evidence changes.

## Supersession example

The original decision block remains unchanged in its period file:

```text
.knowledges/decisions/2026-10.md
```

A later decision is inserted at the top of the same file and records the change:

```markdown
- ID: `DEC-20261029-101500`
- Supersedes: `DEC-20261028-153000`
```

Agents should use the later decision for the affected scope while retaining the earlier decision for historical reconstruction.

## Legacy blocks

Older blocks may use YAML metadata. They remain historical records and must not be rewritten solely to change format. Strict integrity checks still reject missing hashes. For read-only historical inspection, `list_decisions.py --include-unverified-legacy` allows unhashed YAML records with an explicit unverified label; it does not exempt modern Markdown blocks or mismatched hashes. New blocks must use the Markdown-only format above.
